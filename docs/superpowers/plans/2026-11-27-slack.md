# Slack 私聊任务入口

本机用户为一个 Slack 应用配置指定用户 ID、App 级令牌和 Bot 令牌，并指定一个 Kada 配对设备。启动 `npm run harness -- slack` 后，Bot 私聊接收文字和文档。用户在 Bot 原消息的线程回复 `!confirm` 或待答内容，任务在原 daemon 中执行。核验产物通过 Slack 文件上传发回。

Pots 在 Socket Mode 回执前保存事件。重连时用连接前的历史位置补读私聊和已知线程，用消息元数据找回已发送但回执丢失的原消息。Kada 在现有配对接口之上应用这三处行为，并沿用已入库的原消息和核验产物。 [Pots 的先保存后回执](https://github.com/Crokily/pi-durable-bot/blob/38486add7c1f/src/channels/slack/sdk.ts#L34) · [Pots 的历史补读](https://github.com/Crokily/pi-durable-bot/blob/38486add7c1f/src/channels/slack/index.ts#L701) · [Pots 的发送回执查找](https://github.com/Crokily/pi-durable-bot/blob/38486add7c1f/src/channels/slack/index.ts#L770)

- 只受理配置用户和 Bot 的一对一私聊。Socket Mode 回执在保存事件后返回。私聊和任务相关线程从已保存的时间位置补读，历史消息与实时消息按原时间戳去重。
- 确认绑定显示的任务摘要和修订。回复主任务或子任务的原消息会路由到原问题。`!new` 开新会话，`!status` 可重新显示当前待办，`!delivery` 可明确请求再发核验文件。
- 原附件经 Slack 文件 API 和已有配对接口校验。文字标记发送 ID，重连时按原消息查回回执。文件使用 Slack 当前的外部上传与完成 API。 [Slack 外部上传流程](https://docs.slack.dev/messaging/working-with-files/#uploading_files)
- 本地 Slack Web API、WebSocket 和真实 Kada daemon 验证先保存再回执、重复消息去重、原确认和文件字节。另在回执已返回、文档尚未读完时强制终止 CLI，再启动后用本机记录接回任务。断线后按时间分页找回丢失回执的 Bot 消息，再补读这些消息的原线程。测试覆盖答复在连接器和 daemon 都停止期间到达的场景。线程和文件查询按 Slack 要求使用表单编码。 [Slack 端到端回归](../../../test/slack.test.ts) · [Slack 线程 API](https://docs.slack.dev/reference/methods/conversations.replies/)
