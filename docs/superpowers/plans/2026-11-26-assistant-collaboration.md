# 持久跨助手协作实施计划

> 按superpowers:executing-plans与TDD沿原Fork功能分支实施。此计划尚未执行；原生实验只决定公开扩展点，不算产品交付。

**Goal:** 用户指定项目助手在同一来源会话内接收独立工作，保留同事历史、原任务/文件/结果身份，支持排队、补充、返工和停止，跨多跳不扩大权限与预算。

**Spec:** [完整契约和验收清单](../../specs/2026-11-26-assistant-collaboration.md)。

**Architecture:** 原Pi后台锚点持有同事conversation，原生持久deliver/report任务承载投递和回交。业务文档保存角色pin、原工作及回执。模型、执行、等待、重试、压缩、恢复与用量沿Pi；主目标仍是唯一交付与预算来源，无第二调度/数据库/消息总线。

## Global Constraints

- 配置与派活分开；只在原已确认执行目标内受理，普通聊天/准备/旧/远程任务不自动获得执行授权。
- 同事实际工具是来源能力、根目标授权和目标角色名单交集；原控制工具不能用于提交根目标，角色/目录变化不静默扩大旧范围。
- 全部工作计入原Harness用量；停止、取消、预算、目标修订和迟到报告绑定原ID/版本，不补预算、不自动重派。
- 站立/new/已有会话及返工分别明确，不把临时子任务结果或元数据字段称为完整持久团队。
- 保留原文件/历史/配置/凭据，用户停止决定优先，未知外部结果不能自动重放。
- Fork提交和推送，无上游PR。所有剩余Spec项继续保留，不能靠只实现普通派活缩减验收。

## Review Focus

主目标并发submit与派活的事务竞态；后台边界越过普通abort；原站立会话权限改变后复用；目标版本/归档与已有工作继续；回交与用户停止/目标修订；循环和等待环；二进制输入复制时变更。每项在所属步骤以实际副作用或原状态断言覆盖。

### Task 1：原业务身份及事务边界

新增`src/assistant-peer-state.ts`，仅定义Pi文档/类型与原工作只读投影；新增`test/assistant-peer-state.test.ts`。状态包含来源Goal修订/epoch、发起/目标conversation、角色/有效范围pin、原工作说明、原消息/结果关联、文件快照、父链和停止决定。任务状态仍取Pi原submission/task。

- [ ] 先失败测试：原请求相同内容返回同一记录、异内容冲突；角色与原权限固定；状态投影不复制私有历史；旧任务无文档仍沿旧路径；已取消/过期来源不得认领。
- [ ] 在同一次Pi事务认领原工作和原生任务，禁止先声称受理后另写运行记录。`Goal.task_submit`在原事务检查必要工作已结清，防止并发assign后过早交付。
- [ ] 明确站立会话相容键（来源conversation、角色ID/修订和有效范围）；new独立建立，已有工作返工引用原记录，不根据最新目录重算旧配置。

### Task 2：持久同事与原消息/结果

新增`src/assistant-peers.ts`作为Pi扩展，使用已验证锚点与deliver/report原生task；角色scope从各自conversation文档读取。复用`Assistants.select`、`AssistantPin`及既有工具选择/校验，按需提取原policy纯判断供共享，不复制registry或Agent循环。

- [ ] 先失败的真实Pi测试：同事第一次/第二次工作、standing/new/已有会话、各自指令/模型和有效工具；关闭/重开及压缩保留历史，原输入/结果只投递一次。
- [ ] 忙时followUp排队、补充指导和原问题答复分别保存；拒绝向自身/祖先/等待环，限制深度/根工作数量，并保留原用户停止决定。
- [ ] 执行阶段只读目录提供原角色/同事/工作元数据，配置管理权限不扩大；主/子/嵌套/加载/Skills/命令核验沿固定交集。单一registry不能让后注册的目标角色覆盖其他同事策略。
- [ ] root模型/同事模型分别核对Pi原生压缩与目录可用性；缺少模型直接失败，不换供应商。实际用量只从原Pi文档汇总。

### Task 3：固定文件与回交证据

复用`Workspace.inspect`和现有原子复制/哈希规则，以原工作身份安排输入目录和产物引用；不要把模型给出的路径当作成功复制。

- [ ] 先失败测试：原文件SHA-256、二进制/空文件、复制期间修改、大小/路径/链接边界，失败不留下已成功受理的假回执。
- [ ] 原输入与结果版本分开，返工保留原说明与旧产物；主助手仍按原目标独立核验，结果数据不成为授权。

### Task 4：Runtime停止、预算、待答及视图

修改原`src/runtime.ts`、`src/goal.ts`、`src/task-view.ts`的真实边界，不另建监督器。新本机任务固定特性/项目标记；原默认临时delegation及旧任务保持。

- [ ] 先失败测试：目标修订、暂停/取消、时限/token到限使原工作停止，迟到结果不唤醒旧目标；已认领及排队任务不在恢复时补预算。
- [ ] Goal完成前必须结清必要工作与用户问题；根task_status显示原同事/工作/文件/用量。答复绑定原工作/问题，来源不存在或旧版本拒绝。
- [ ] 两位同事各自停止/中断、保留其他有效工作，旧停止点击不能停止后来工作；原角色变化/归档及model不可用按Spec明确处理。

### Task 5：owner入口与真实恢复验收

沿原owner API、终端及任务视图提供列出、读原结果、回复问题、停止指定原工作的路径；手机/原生端未接入时明确保留缺口。

- [ ] API/CLI先失败测试，验证原ID/版本、跨项目/远程权限、历史恢复及当前停止对象；不增加全局主令牌共享。
- [ ] 实际SIGKILL覆盖认领、已投递未回执、已决定结果、报告后未回执、停止及新工作入队窗口；独立计数模型/工具实际副作用。
- [ ] 硅基流动合成资料完成同事多份工作、原历史回忆、答复/返工及主目标交付；保留失败和费用未知，不用“说已交付”替代原产物检查。
- [ ] 同模型/工具/权限的原Pi机制为基线，对照恢复、完成率、人工介入和用量；一次样本不证明净收益。
- [ ] 类型、聚焦/必要全量、笔记/提交检查及独立复核按实际证据记录；推送Fork无上游PR。完整Spec仍有未覆盖项时继续，不将目标标为完成。
