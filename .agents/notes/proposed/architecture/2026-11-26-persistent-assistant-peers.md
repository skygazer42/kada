# Agent Note: 持久同事会话复用Pi后台归属与回交

Status: proposed

## Problem

具名角色配置与单目标临时workers不能表达同一同事的多份工作、原历史、返工和独立结果。跨回合后台工作若没有原归属、回执和停止边界，会在恢复时重复派发，或在用户取消/预算停止后继续执行与回传。

## Proposal

复用已安装Pi1.4.0官方示例的后台锚点conversation与持久deliver/report任务，业务文档仅保存原助手/工作/文件和进度关联。每位同事从自己的已提交conversation文档读取角色pin及有效工具范围，共用一个registry，主目标仍是唯一预算及最终交付来源。不增加运行器、调度器、队列、数据库或消息总线。

后台锚点跨主回合存在，但Kada暂停/取消与预算规则继续要求完整子树停止；不能直接采用官方示例普通Esc跳过后台的产品政策。来源、目标、原Goal修订/epoch、停止版本、文件哈希与原回执须在实际边界检查。完整产品契约和计划见[持久协作Spec](../../../../docs/specs/2026-11-26-assistant-collaboration.md)。

与[角色固定范围](../../implemented/architecture/2026-11-26-named-assistant-scope.md)部分重叠：原决定负责已实现的角色配置与scope，本提案负责未来同事工作生命周期，不把已实现内容移成提案。原个人助手服务继续持有Pi为唯一执行来源的决定，没有被取代或过时提案需要归档。

## Alternatives considered

给现有delegate加角色名称成本最低，但每次创建新子会话不能保留同事历史，故不能当作持久团队。所有同事放在ownerless会话更简单，但会失去来源子树取消与原归属，恢复和预算更难解释。

复制参考项目的协调运行时/数据库可获得现成调度，却违反Pi优先并重复执行状态。官方后台锚点与reporter已经提供归属和恢复机制，只适配业务身份与验收。

每个角色注册带闭包的同名policy可能使同一registry后注册的角色覆盖其他同事；每个同事另开registry/运行时又扩大基础设施。原生实验确认从各自conversation文档读取角色pin可隔离提示与权限，后续用此公开扩展点实现。

## Acceptance criteria

完整Spec的原会话、standing/new、排队、补充/待答、返工、循环/总量、文件传递、权限/预算与停止、迟到结果、SIGKILL和用户入口均须实测。已完成的四个原生机制测试与22项相关回归只证明扩展点可用，产品尚未实现，不能据此转implemented。

阶段1的Pi业务文档、认领/回执/停止事务及Goal的opt-in约束已实现，21项核心测试及公开类型检查通过，实际SQLite重开保留原身份与停止。Runtime尚未启用派活；文件、工作指导/待答、用户控制和完整产品验收未完成，所以本决定仍为proposed。

内部派活扩展已实现，包含固定角色和权限的 standing/new/已有会话、原答案回交与显式返工。返工单独记录 `reworkOf`，目录编辑/归档后仍使用原 pin；消息和报告使用稳定原 Pi 请求，来源等待用户时持久睡眠，恢复后回传。父工作从当前原生输入关联识别，不维护可被后续排队覆盖的“当前工作”。报告只带出已复制投影与标量，不能让 Pi 事务 draft 逃逸。

当前 35 项聚焦通过，包含 11 项派活集成及 3 项真实 SIGKILL；后者覆盖派活回执、非安全重放的外部动作回执和原报告回执，检查实际文件计数与原输入/报告不重复。Runtime、文件、提问/指导、精确停止与预算和 owner 入口仍未完成，不据此将本提案转 implemented。

阶段1相关组合55项通过，涵盖原Pi机制、固定角色、临时委派、Runtime、准备确认与恢复。当前派活阶段整仓回归 578 通过、0 失败、4 项可选 Office 跳过，另加的选择性停止原生探针 1/1。类型/构建、严格公开类型与笔记/提交检查通过。没有新的真实模型或独立审查通过结论；子代理仍未收到正文，CLI 本地快照因 Windows 访问时间变化拒绝，作者验证与独立审查分开。

## Risks

后台边界会跳过普通abort，若漏接主目标停止会继续工作。报告可能在旧Goal或停止之后到达，必须留原结果且不能唤醒失效来源。多跳和站立历史复用需要原角色/有效范围的相容键，防止循环或权限扩张；角色工具名单不是OS沙箱。

原生实验使用合成模型与真实SQLite，不验证供应商费用、任务质量、外部应用或原生设备。后续若公开API不能完整承载某个要求，需补实际证据和设计，不静默收窄目标。

Pi在首个表写入后不允许再读取原表。阶段1从原生分配返回的创建记录验证归属，所有读取和权限检查置于分配前，数据与原生任务一起回滚。结果和报告使用原submission关联；同一报告回合提交Goal不等待自身done，以免循环等待。停止与总量不能被根修订/epoch刷新清掉，owner重新授权需后续显式入口，不给模型自清除。

选择性停止的追加原生探针已通过：取消 `LiveDoc.run.taskId` 只终止该轮模型/工具与已放置输入，保留同会话的 queued followUp。随后原 Pi 被动 write（空 model、非输入）触发 final boundary，原第二份输入只执行一次，无新增用户指令。不能用 `Conversation.abort()` 替代，因为它会撤回该会话其他排队输入；尚须把此机制接到业务停止回执、后代清理和预算/修订控制。
