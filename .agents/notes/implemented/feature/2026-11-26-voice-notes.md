# Agent Note: 原会话录音回执与答复语音

Status: implemented

## Problem

用户需要把录音的转写发进正在使用的原会话，并朗读其中已经保存的答复。供应商调用与 daemon 进程的寿命不同，重复发送会造成重复模型输入或语音调用。

## Decision

本机语音便笺由 owner 从原会话入口发起。WAV 读取复用工作区边界和不可变快照检查。转写调用前保存原请求与源哈希，完成后写入 Pi 会话回执。用户提交转写时沿原 Pi 输入的固定请求 ID。朗读捕获已有答复条目，WAV 经原子发布后保存哈希，打开前重新核验。

语音供应商与模型使用硅基流动已有环境变量认证。受理与保存之间的网络调用在会话变更锁之外执行。发生供应商调用但未保存回执后，原请求保留已受理状态。 [源代码参考与用法](../../../../docs/superpowers/plans/2026-11-26-voice-notes.md)

手机 Web 的听写仅在配对门户使用。服务器直接把收到的音频交给既有转写方法并返回文字，页面沿原草稿入口保存。最终发送继续走原消息回执。切换会话会放开麦克风并取消页面等待。 [源码与验收](../../../../docs/superpowers/plans/2026-11-27-phone-dictation.md)

手机播放在当前配对的私有会话读取指定 Pi 答复。合成回执保留原答复编号。服务端核验 WAV 快照后发送已经核验过的同一份内存字节，页面切换会话时停止播放器并释放音频。

## Alternatives considered

把音频上传直接当成普通模型输入可以省去转写回执，但会增加模型格式耦合，也妨碍用户核对识别结果。独立转写让原文本可查看并可按同一身份送入原会话。

每次播放重新合成可以少存一个文件，但会重复产生供应商调用，并可能朗读后来的答复。保存原条目和音频哈希可复用原结果。

## Consequences

聚焦测试覆盖工作区边界、同一次转写、请求中断、重启、后续答复和被修改的 WAV。CLI 使用硅基流动完成转写和合成。Chromium 用模拟麦克风和合成供应商验证录音、取消、草稿和发送。实体手机与扬声器待验收。 [供应商实测](../../../../docs/experiments/2026-11-26-voice-notes-siliconflow.json)
