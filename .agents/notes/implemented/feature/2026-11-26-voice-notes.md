# Agent Note: 原会话录音回执与答复语音

Status: implemented

## Problem

用户需要把录音的转写发进正在使用的原会话，并朗读其中已经保存的答复。供应商调用与 daemon 进程的寿命不同，重复发送会造成重复模型输入或语音调用。

## Decision

语音只由本机 owner 从原会话入口明确发起。WAV 读取复用工作区边界和不可变快照检查。转写调用前保存原请求与源哈希，完成后写入 Pi 会话回执。用户提交转写时沿原 Pi 输入的固定请求 ID。朗读捕获已有答复条目，WAV 经原子发布后保存哈希，打开前重新核验。

语音供应商与模型使用硅基流动已有环境变量认证。受理与保存之间的网络调用在会话变更锁之外执行。发生供应商调用但未保存回执后，原请求保留已受理状态。 [源代码参考与用法](../../../../docs/superpowers/plans/2026-11-26-voice-notes.md)

## Alternatives considered

把音频上传直接当成普通模型输入可以省去转写回执，但会增加模型格式耦合，也妨碍用户核对识别结果。独立转写让原文本可查看并可按同一身份送入原会话。

每次播放重新合成可以少存一个文件，但会重复产生供应商调用，并可能朗读后来的答复。保存原条目和音频哈希可复用原结果。

## Consequences

聚焦测试覆盖工作区边界、同一次转写、请求中断、重启、后续答复和被修改的 WAV。实际 CLI 使用硅基流动完成转写和合成。麦克风、手机语音及实体扬声器验收仍在能力对照表内。 [供应商实测](../../../../docs/experiments/2026-11-26-voice-notes-siliconflow.json)
